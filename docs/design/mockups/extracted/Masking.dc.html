Recordings contain sensitive data

Treat a recording like the traffic it came from

A recording is a verbatim log of everything a client and a server said to each other, customer data included. Credentials are masked at the moment the event is written — never stored in the clear and hidden at display time. The output directory is git-ignored; a fleet refuses an --out-dir git could commit.

Blanked

Everything that looks like a credential: keys whose name carries auth, cookie, sessionid, api_key, token…; Bearer … in text; every --mask-key NAME you add. The value is gone; its place in the message is listed in redactions.

Handle pseudonym

Two fields exist only to tie messages together: params.progressToken and params._meta.progressToken. They get a stable stand-in from the run’s keyed HMAC: the same value reads the same way throughout one recording and differently in the next. The relation survives, the value does not. Over HTTP, SSE event ids join this set.

A session id grants access to the session. It is closer to a bearer token than to a correlation id, so Mcp-Session-Id is blanked, not pseudonymised — the recording keeps only an ordinal (session 1, 2, …).
