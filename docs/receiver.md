# The callback receiver

A small standalone HTTP service that accepts callbacks from audited servers. It keeps, per
registered audit, only what is needed to match a callback to the payload that caused it, and
it deletes that on a fixed schedule. It runs on the auditor's own host and is operated over
SSH. Standard library only; POSIX only (it locks with `flock`).

```sh
python -m mcp_kymograph.receiver <serve|register|pull|purge> --data DIR ...
```

## Purpose and data model

A payload tells the audited server to fetch `https://<receiver-host>/<prefix>/<rest>`. If the
server does, the receiver records one entry. `<prefix>` names the registered audit and is a
secret of its own (at least 128 bits of randomness); `<rest>` carries the identifier of the
payload. No probe of this version builds a receiver URL: a payload reaches a server only where
the operator puts it, for instance into the arguments of a script's call.

**An entry holds:**

- a running number (per prefix, from 1), the time (UTC), the sender address, the scheme, the
  method and the `Host` (its labels that are not names hashed, see below);
- the path (`<rest>`), in which each run of segments that are not names is replaced by one
  `hmac:<hex>`;
- the names of the query parameters, and for each value only its HMAC-SHA-256;
- the names of all headers, as received;
- for `Authorization`, `Proxy-Authorization`, `Cookie` and each registered secret header:
  `{"present": true, "scheme": ..., "hmac": ...}`. `scheme` is the first word of an
  `Authorization` value when it is letters only, at most 16 of them, and followed by
  credentials; otherwise `null`. A value that is one bare word is the credential and is never
  taken for a scheme. `hmac` is the HMAC-SHA-256 over the whole value, hex, under the
  registration's key. Repeated headers are joined with `, ` first;
- of the body, only the size and the SHA-256.

**What a name is.** The sender chooses these names, so one is stored as it came only when it
looks like a name, and anything else is treated like a value: kept as an HMAC under the
registration's key, never in plain text.

A name matches `^[A-Za-z][A-Za-z_.-]{0,28}[0-9]{0,3}$`: it starts with a letter, has at most 32
characters, and digits only at the end, at most three. `state`, `code`, `redirect_uri`,
`client_id`, `id_token` and `v2` are names. A `ghp_` token, hex, a UUID, a number and a
base64url token with digits are not: they are too long, or start with a digit, or have digits
in the middle. The rule applies to query names, path segments and the labels of `Host`.

- Query: a name followed by `=`. An element without `=`, or with anything else in front of
  the `=`, is a value without a name. All such elements together (decoded, joined by `&`) are
  kept as **one** HMAC under the fixed name `(unnamed)`.
- Path (`<rest>`): split at `/`. An empty segment and a name are kept. Consecutive other
  segments become **one** `hmac:<hex>`, the HMAC of the decoded segments joined by `/`.
- `Host`: split at `.` into labels, treated like path segments (a run of labels that are not
  names is one `hmac:<hex>` over the labels joined by `.`). A port, after the last `:`, is
  kept when it is 1 to 5 ASCII digits and at most 65535 (the length is checked before the
  number is made); otherwise the whole value is treated as labels.
- Header names: the rule from before: only at most 64 characters from `A-Za-z0-9-`. Any other
  header name is not stored, neither in the list of names nor anywhere else; each is counted
  under `invalid_header_name` (see below).

**What the rule does not catch.** A short token made only of letters, `_`, `.` and `-`
(with at most three digits at the end) is indistinguishable from a name, and is stored as it
came. The rule keeps the service from storing what is plainly not a name; it cannot hide a
value that looks like one.

**An entry does not grow with the request.** At most `MAX_STORED_PARTS` (32) parts are stored
for a path, a query and a `Host` each; what is beyond them is one HMAC together (in a query, it
joins the `(unnamed)` HMAC). Names kept as they came are never longer than the request that
carried them, so an entry is at most the size of its request plus a fixed span. The span is the
fixed fields, the three always-secret headers and each registered secret header (about 150
bytes each), and for a path, a query and a `Host` at most 32 parts of at most 70 characters:
in all not more than about 12 KiB, and about 1 KiB for a typical registration. A request of
16 KiB made of `/~/~/~...` or `?~&~&~...` gives an entry of well under 2 KiB.

**Never stored:** a header value, a query value, or any part of a body. `Host` is the one
value kept in part: its labels that are names and its port.
The HMAC key is generated by the auditing side, is stored with the registration, and is
deleted with it; the audited server never sees it.

**Everything else** is only counted, one number per day in `counts.json`: a request to an
unknown or expired prefix, to any other path, one that is not valid HTTP, one over a limit,
and one that arrives after a cap is reached. Nothing of such a request is kept.

**The answer is always the same**, for every request, recorded or not: `200`, an empty body,
`Content-Type: text/plain`. Nothing is echoed. The one exception is a connection past
`MAX_CONNECTIONS`: it is closed without an answer, because it is closed before it is read, and
before reading there is no request to answer. It is counted in memory only (the accepting
thread never touches the disk) under its own name, `over_connection_limit`, and the sweep
carries the number into `counts.json` for the day.

### Files

The data directory must exist and be mode `0700` and owned by the running user; otherwise
every command stops with a message. All files in it are `0600`.

| File | Content |
| --- | --- |
| `reg-<prefix>.json` | the registration, including the key |
| `state-<prefix>.json` | next running number, entry count of the current hour |
| `entries-<prefix>.jsonl` | the entries, one per line |
| `counts.json` | unrecorded requests per day (UTC), the last 90 days; connections past the limit per day under `over_connection_limit`; deleted damaged registrations per day under `unreadable_registration`; registrations whose deadlines a sweep could not enforce, per day under `sweep_error`; header names not stored per day under `invalid_header_name`; requests whose handling raised, per day under `handler_error` (a number only, nothing of the request); `unreadable_counts` (below) |
| `.lock` | held while anything changes |

## Commands

**`serve --data DIR --port N`** accepts requests on `127.0.0.1:N`. It speaks plain HTTP only.
`N=0` picks a free port and prints it to stderr.

**`register --data DIR`** reads one registration as JSON from stdin. The key is never an
argument: an argument shows in the process list and in shell history.

```json
{
  "prefix": "<22+ chars base64url>",
  "key": "<base64, 32+ bytes>",
  "expires_at": "2026-12-01T00:00:00Z",
  "retention_seconds": 604800,
  "secret_headers": ["X-Api-Token"]
}
```

- `prefix`: base64url characters (`A-Za-z0-9-_`), 22 to 128 of them (22 carry 132 bits), of
  which at least 10 are different (`MIN_PREFIX_DISTINCT_CHARS`); a prefix such as 22 times `a`
  is refused.
- `key`: standard base64, 32 to 1024 bytes after decoding.
- `expires_at`: end of the audit window, ISO-8601 with `Z` or `+00:00`. A time that is not
  after now is refused, and so is one more than 366 days after the moment of registration
  (`MAX_EXPIRES_AHEAD_SECONDS`): no audit runs that long, and the bound keeps
  `expires_at` plus retention far from the end of the supported date range.
- `retention_seconds`: 1 to 90 days.
- `secret_headers`: up to 32 header names, matched case-insensitively. `Host`,
  `X-Forwarded-For` and `X-Forwarded-Proto` are refused: the service stores the first in plain
  text and evaluates the other two itself, so none of them can be kept secret.

The check is strict: an unknown key or a wrong type is refused with its place
(`$.secret_headers[1]: expected a string`), and so is a prefix that is already registered.

The rules on distinct prefix characters, on plain-text headers in `secret_headers` and on
`expires_at` apply to `register` only. A registration already stored is loaded with the check
of form and types alone, so a rule added later never cuts off an audit that is running. A name
in the stored `secret_headers` with exactly one trailing line feed is taken there (older
receivers took one); it matches no received header, and `register` refuses it. A stored
registration that cannot be read as one (damaged: the file exists, but its JSON, its form or
its types are wrong, or its deadline lies beyond the supported date range) is deleted whole at
the next sweep: registration, key, state and entries. It is counted per day under
`unreadable_registration`; the key never stays behind. A registration whose prefix fails only
by a trailing line feed (receivers before prefixes were matched whole took one, counted in the
length) is handled the same way, and leftover `state` and `entries` files of such a prefix go
too.

**`pull --data DIR --prefix P [--after N]`** sweeps, then writes the entries of that prefix
with a running number above `N` to stdout as JSON Lines. If the registration is gone (past
`expires_at` plus retention, purged, or damaged) it writes one line to stderr and exits with
3. If the sweep before it could not enforce the deadlines of this registration, it writes one
line ("deadlines of this registration could not be enforced") to stderr, prints no entry and
exits with 1. If the registration file cannot be read at the moment (an `OSError`), it writes
one line to stderr, prints no entry and exits with 1: an unreadable registration is not an
empty result.

**`purge --data DIR --prefix P`** deletes key, registration and entries at once and confirms
in one line. If the registration was damaged it is deleted all the same, but the line goes to
stderr and the exit code is 3.

Exit codes: `0` done; `1` data directory unusable, or the sweep before `pull` failed or could not
enforce the deadlines of that registration, or the registration could not be read (one line on stderr, no traceback); `2` input refused; `3` `pull` found no
registration, or `purge` found only a damaged one.

### Deletion does not depend on anything else

Deleting what is bound to a deadline, or what is damaged, never fails because of something
else.

- The sweep handles each registration on its own. An error with one ends the handling of that
  one, never the sweep over the others (`KeyboardInterrupt` and `SystemExit` excepted). A
  registration that is due or damaged is deleted whole: key, `state` and `entries`.
- Any other error while a registration is handled (a file that cannot be read now, a removal or
  a rewrite that fails, a deadline that cannot be worked out) deletes nothing. The registration
  stays, the error is counted under `sweep_error`, and the sweep remembers the prefix as not
  enforced. `pull` of such a prefix prints no entry and exits with 1.
- Reading does not hang on deleting: `pull` leaves out every entry whose time plus
  `retention_seconds` has passed, and everything of a registration whose `expires_at` plus
  retention has passed, whether the sweep could delete them or not.
- Leftover `state` and `entries` files are removed only for a prefix whose registration file is
  missing. A registration that exists but cannot be read keeps its files.
- Removal comes first, counting second, in the sweep and in `purge`. If counting fails, the
  deletion is already done.
- `counts.json` is checked on every level: an object, a day as key (or one of the names above),
  a non-negative integer as value. Content that is not exactly that is replaced at the next
  write, and the loss of the old counts is itself counted: `unreadable_counts` with the value 1.
  A file that cannot be read at the moment (an `OSError` such as too many open files) is not
  damaged: it is left as it is and the numbers wait in memory for the next try.
- Every count goes the same way. If `counts.json` cannot be read or written (`OSError`), the
  increase stays in the memory of the process and is written with the next successful write.
  What is still in memory when the process ends is lost.

### Deadlines

- An entry is deleted `retention_seconds` after its time, pulled or not.
- After `expires_at` the prefix counts as unknown: requests to it are only counted. Entries
  can still be pulled until their own retention ends.
- Registration and key are deleted at `expires_at + retention_seconds`.
- A sweep runs in the service every 30 seconds, and `pull` sweeps before it reads.

## Limits

All are named constants in `src/mcp_kymograph/receiver/limits.py`.

| Constant | Value | Effect past it |
| --- | --- | --- |
| `MAX_HEADER_BYTES` | 16 KiB | request line and headers; counted, not recorded |
| `MAX_BODY_BYTES` | 1 MiB | the rest is discarded; the entry's body says `"truncated": true` and a size of the limit |
| `CONNECTION_TIMEOUT_SECONDS` | 10 | total time per connection; counted |
| `MAX_CONNECTIONS` | 64 | the connection is closed unanswered and unread; counted as `over_connection_limit` |
| `MAX_ENTRIES_PER_HOUR` | 1000 | per prefix and UTC hour; counted |
| `MAX_DATA_BYTES` | 64 MiB | whole data directory; counted |
| `SWEEP_INTERVAL_SECONDS` | 30 | |
| `COUNT_DAYS` | 90 | days of counters kept |
| `MAX_EXPIRES_AHEAD_SECONDS` | 366 days | `expires_at` further ahead than this is refused at `register` |
| `MAX_NAME_CHARS` / `MAX_NAME_DIGITS` | 32 / 3 | a longer query name, path segment or label of `Host`, or one with more digits or digits not at the end, is not a name |
| `MAX_HEADER_NAME_CHARS` | 64 | a longer header name is not stored |
| `MAX_STORED_PARTS` | 32 | parts stored per path, query and `Host`; the rest is one HMAC |
| `MIN_PREFIX_CHARS` / `MAX_PREFIX_CHARS` | 22 / 128 | prefix length; refused at `register` |
| `MIN_KEY_BYTES` / `MAX_KEY_BYTES` | 32 / 1024 | decoded key; refused at `register` |
| `MAX_RETENTION_SECONDS` | 90 days | refused at `register` |
| `MAX_SECRET_HEADERS` | 32 | refused at `register` |

The service never opens a connection of its own, not even to resolve a name.

## Operation

### TLS proxy

The service has no TLS. A proxy in front terminates 443 and passes 80 through unchanged.
Schema and sender come from `X-Forwarded-Proto` and `X-Forwarded-For`, and are believed only
when the connection comes from 127.0.0.1 (the last address of `X-Forwarded-For` is used).
Anything else is recorded with the connection's own address and `http`. The proxy must
therefore run on the same host and must overwrite these headers, not append to what a client
sent.

Example with Caddy (global options and one site; adjust to the installed version):

```caddyfile
{
	# No HTTP-01 and no redirect: port 80 must reach the service as plain HTTP, since an
	# audited server may call http:// too. The certificate comes by TLS-ALPN-01 on 443 only.
	auto_https disable_redirects
	servers {
		trusted_proxies static   # trust nobody: client-sent X-Forwarded-* is replaced
	}
}

<receiver-host>:443 {
	tls {
		issuer acme {
			disable_http_challenge
		}
	}
	# No access log at all; a log with headers would keep what the service refuses to keep.
	reverse_proxy 127.0.0.1:8080 {
		header_up X-Forwarded-Proto {scheme}
		header_up X-Forwarded-For {remote_host}
	}
}

http://<receiver-host>:80 {
	reverse_proxy 127.0.0.1:8080 {
		header_up X-Forwarded-Proto {scheme}
		header_up X-Forwarded-For {remote_host}
	}
}
```

Ports 80 and 443 are open to the world and go to the proxy. Port 8080 (the service) is not
reachable from outside.

### Administration

Registration, pulling and purging run over SSH, and SSH listens only inside a WireGuard
tunnel (`<wireguard-port>/udp` is the only other open port). Nothing is administered over
the public interface. Run the service as its own user with a data directory it owns:

```sh
install -d -m 700 /var/lib/receiver
python -m mcp_kymograph.receiver serve --data /var/lib/receiver --port 8080
```

### Host names

Certificates are logged publicly in Certificate Transparency logs. The host name must not
contain a customer name, an audit name or anything else that says whom you audit.
